# 📄 mozaicScript 所有権・借用システム拡張追加仕様書 (Formal Revision Specification)

本文書は、mozaicScript 言語仕様書、コアライブラリ仕様書、中間表現仕様書、および実行エンジン仕様書に対する「メモリ安全性の自動化」と「実行速度の極大化」を両立するための機能拡張および変更定義を厳密に規定する。

本仕様の追加により、ユーザーコード（`.moz`）における手動のメモリ解放（`free`）は完全に撤廃され、コンパイラフロントエンドが静的解析に基づいてライフサイクルを完全に管理する。本定義は、仕様書作成担当者および実装担当者が迷うことなく、一貫性と矛盾のないコンパイラ・ランタイムを構築するための絶対的な基準（MUST）である。

---

## 1. 概要および基本原則 (Architecture & Core Philosophy)

### 1.1 開発者体験（DX）の完全な妥協と性能の追求
本拡張は開発者の記述負荷を軽減することを目的としない。すべてを明示的に記述させ、暗黙の解釈を徹底的に排除することで、コンパイラフロントエンドが100%の確証を持ってメモリの生存期間と安全性を追跡できるようにする。

### 1.2 フロントエンドとバックエンドの完全な分離の維持
* **フロントエンドの義務（MUST）：** 所有権の移動（ムーブ）、不変借用・可変借用の整合性チェック、および生存期間（ライフタイム）の静的解析をすべて行い、ルール違反をコンパイルエラーとして弾く。また、安全性が静的に証明されたASTに対して、メモリ解放命令（`__builtin_free` および `drop` メソッド呼び出し）を適切な位置に**破壊的に自動挿入**した上で、JSONの中間表現を出力しなければならない。
* **バックエンドの義務（MUST）：** 所有権の追跡や借用の検証といった重厚な静的解析を一切行ってはならない（信頼してよい）。バックエンドは、フロントエンドから渡されたJSON ASTに記述されている命令（自動挿入された解放命令を含む）を上から順に機械的にターゲットコード（C、WASMなど）へ lower することのみを責務とする。

## 2. 型システムの拡張定義 (Type System Extensions)

既存の型システム（仕様書 §4）に対し、値の所有・参照の状態を表す3つのセマンティクスを導入する。これらは中間表現（JSON AST）の `resolvedType` 文字列において厳格に区別されなければならない（MUST）。

### 2.1 所有権型 (Ownership Type)
* **表記・表現：** 既存の型名そのもの（例：`i32`, `Array<f32>`）。
* **意味論：** その値のメモリ領域を直接管理する唯一の「所有者」であることを示す。ある時点で値の所有者は必ず世界に1人だけでなければならない。スコープの離脱または生存期間の終端において、所有権が他へ移動していない場合、そのメモリは強制的に破棄される。

### 2.2 不変参照型 (Shared Reference Type)
* **表記・表現：** 型名の先頭に `&` を付与する（例：`&i32`, `&Array<f32>`）。
* **意味論：** 値の所有権を持たず、対象を「読み取り専用」として一時的に借用する。同一の値に対する不変参照は、同一の生存期間内に**同時に無限個存在することを許可する**。ただし、後述する可変参照とは絶対に共存できない。不変参照型を経由したフィールドへの代入や変更メソッドの呼び出しは、コンパイルエラーとしなければならない（MUST NOT）。

### 2.3 可変参照型 (Exclusive Reference Type)
* **表記・表現：** 型名の先頭に `&mut ` を付与する（例：`&mut i32`, `&mut Array<f32>`）。
* **意味論：** 値の所有権を持たず、対象を「読み書き可能」として一時的に借用する。可変参照は、その生存期間内において**世界にただ1つしか存在してはならない（排他性の完全保証）**。他の不変参照、あるいは他の可変参照と同一の値に対して同時に共存することは一切禁止される。可変参照型を経由したフィールドへの代入、および変更メソッドの呼び出しが許可される。

### 2.4 型の同一性（Type Identity）の修正
仕様書 §4.6 に対し、修飾子（`&`, `&mut`）が異なる場合は**完全に異なる型**として処理しなければならない（MUST）。暗黙の型変換（例：`i32` から `&i32` への自動変換、あるいは `&mut i32` から `&i32` への自動キャスト）は、仕様書 §4.4 に基づき**いかなる文脈でも絶対禁止（MUST NOT）**とする。

## 3. 構文規則の変更と追加 (Syntax Specifications)

### 3.1 メソッド宣言における `mut` プレフィックス修飾子
クラスのメソッドが、自分自身（`this`）の内部状態（フィールド）を書き換える、あるいは他の `mut` メソッドを呼び出す場合、関数宣言の先頭に `mut` 修飾子を付与することを必須とする（MUST）。

```typescript
// 構文定義
アクセス修飾子 [mut] [gpu] function 識別子(引数リスト): 戻り値型 { 本体 }

```

#### 3.1.1 `mut` の有無による `this` の型定義ルール

コンパイラは、メソッド内部における特殊識別子 `this` の型（`resolvedType`）を以下のルールに従って決定しなければならない（MUST）。

* `mut` 修飾子が付与されている場合： `this` の型は **`&mut クラス名`** となる。
* `mut` 修飾子が付与されていない場合： `this` の型は **`&クラス名`** となる。

`this` が `&クラス名`（不変参照）であるメソッド内部から、`this` のフィールドへ代入を行う行為、または `mut` の付いた他のメソッドを呼び出す行為は、すべて型チェックフェーズでコンパイルエラーとしなければならない（MUST NOT）。

```typescript
// 具体例 (core.moc)
public class i32 {
    private let bits: _m32;

    // 不変メソッド: this の型は &i32。bits の変更は不可。
    public function operator+(other: &i32): i32 {
        // ✅ 読み取りは許可
        let raw_result: _m32 = __builtin_i32_add(this.bits, other.bits);
        return new i32(raw_result);
    }

    // 可変メソッド: this の型は &mut i32。bits の変更が可能。
    public mut function addAssign(other: &i32): void {
        // ✅ 可変参照なので bits への代入が許可される
        this.bits = __builtin_i32_add(this.bits, other.bits); 
    }
}

```

### 3.2 借用演算子 `&` および `&mut` の追加

値から参照（ポインタ）を生成する際、ユーザーコードの式中で借用演算子を明示することを必須とする（MUST）。

```typescript
let a: i32 = new i32(10);

let b: &i32 = &a;       // ✅ a から不変参照を取得（明示）
let c: &mut i32 = &mut a; // ✅ a から可変参照を取得（明示）

// ❌ 借用演算子の省略による型ミスマッチ（暗黙変換の絶対禁止）
let d: &i32 = a; // コンパイルエラー（型 i32 を &i32 に代入できない）

```

### 3.3 メソッド呼び出し（糖衣構文）における「自動レシーバー参照バインド」の特例

仕様書 §4.4（暗黙変換の禁止）の例外として、オブジェクト指向の記述性を維持するため、メソッド呼び出しのドット（`.`）演算子、および二項演算子の左辺においてのみ、以下の「自動レシーバー参照バインド」をコンパイラのフロントエンドの脱糖ルールとして規定する。

#### ルール：

変数 `x`（型 `T`）に対してメソッド `x.method(args)` が呼び出された、あるいは演算子 `x + args` が記述されたとき：

1. ターゲットとなるメソッドの宣言を確認する。
2. メソッドが `mut` 修飾子を持つ（`this` の要求型が `&mut T`）場合：
フロントエンドは内部的にこれを **`(&mut x).method(args)`** として処理する。
3. メソッドが `mut` 修飾子を持たない（`this` の要求型が `&T`）場合：
フロントエンドは内部的にこれを **`(&x).method(args)`** として処理する。

この挙動は「型変換」ではなく「メソッド呼び出し構文のレシーバーバインド仕様」として位置づけられ、引数（`args`位置）に対する暗黙変換は依然として一切禁止（MUST NOT）される。したがって、引数位置には必ず `&` や `&mut` を明示しなければならない。

```typescript
let a: i32 = new i32(10);
let b: i32 = new i32(20);

// ユーザーコードでの記述：
let c: i32 = a + &b;  // 脱糖後: a.operator+(&b) -> レシーバーバインドにより (&a).operator+(&b)
a.addAssign(&b);      // 脱糖後: a.addAssign(&b) -> レシーバーバインドにより (&mut a).addAssign(&b)

```

## 4. フロントエンド・コンパイラパイプラインの分離 (Compiler Pipeline)

所有権のチェックと自動解放命令の挿入を安全かつ確実に実装するため、フロントエンド（TypeScript側）の処理を以下の独立した4つのフェーズ（パス）に完全分離して実装しなければならない（MUST）。

```
[ソースコード] 
      │
      ▼
【フェーズ1: パース & AST構築】 ── 構文ツリーの生成 (BorrowExpr等の抽出)
      │
      ▼
【フェーズ2: 型解決パス】 ──────── ジェネリクス単一化・完全型名の解決 (resolvedTypeの埋め込み)
      │
      ▼
【フェーズ3: 借用チェック & 】 ── 所有権シミュレーション、ルール違反の検出、
【  Drop/Free命令自動挿入パス】    および __builtin_free / drop のASTへの破壊的挿入
      │
      ▼
【フェーズ4: JSONエクスポート】 ── バックエンド向け JSON AST の出力

```

### 4.1 【最重要】フェーズ3：借用チェックおよび自動挿入アルゴリズム

このフェーズでは、型が確定したASTに対し、制御フローグラフ（CFG）に沿って各変数の「状態空間」を追跡する静的シミュレーションを行う。

#### 4.1.1 変数の状態空間（State Space）

シミュレータは、各識別子に対し以下の状態を管理する。

* `Uninitialized`：宣言されたが、まだ初期化されていない。
* `Alive(Owner)`：所有権を持って生存している。
* `Moved`：所有権が他の変数または関数呼び出しに移動し、実体が空である。
* `BorrowedImmutable(Count)`：不変借用されている。`Count` は現在アクティブな参照の数。
* `BorrowedMutable`：可変借用されている。

#### 4.1.2 厳格な検証ルール

シミュレータは以下の違反を検出した場合、即座にコンパイルエラーを発生させ、処理を中断しなければならない（MUST）。

1. **Use After Move（移動後の使用禁止）：**
状態が `Moved` である変数に対する「値の読み取り」「代入（再初期化を除く）」「メソッド呼び出し」「新たな借用（`&` / `&mut`）」が発生した場合。
2. **Aliasing XOR Mutability（借用排他ルール / XOR原則）：**
* ある変数 `x` の状態が `BorrowedImmutable(Count)`（`Count > 0`）である間、`x` に対する「可変借用（`&mut x`）の生成」「所有権のムーブ」「`mut` メソッドの実行」「直接代入による破壊」が発生した場合。
* ある変数 `x` の状態が `BorrowedMutable` である間、`x` に対する「新たな不変借用の生成」「新たな可変借用の生成」「所有権のムーブ」「あらゆる読み取り・書き込み」が発生した場合。


3. **Lifespan Validity（ダングリング参照の禁止）：**
生成された参照（`&T` または `&mut T`）の生存期間が、その大元（Origin）である変数のスコープ（生存期間）を1ステップでも超えるコードパスが存在した場合。特に関数から参照型を `return` する際、その参照先がローカル変数である場合は、100%コンパイルエラーとしなければならない。

#### 4.1.3 解放命令（`drop` / `__builtin_free`）の自動挿入ルール

シミュレータは、状態が `Alive(Owner)` である変数が、そのスコープ（`BlockStmt`）の終端に達した、あるいはCFG上でそれ以降一切使用されない「生存期間の終端（Liveness End）」に達したことを検知した瞬間、以下の処理をASTに対して破壊的に挿入（インジェクション）しなければならない（MUST）。

1. 対象変数の型（クラス定義）をチェックする。
2. そのクラスが `public function drop(): void` という名称のシグネチャを持っている場合：
ASTの当該位置に、その変数をレシーバーとする **`MethodCall`（`method: "drop"`）ノードを挿入**する。
3. その後（または `drop` メソッドを持たない場合）、対象変数のメモリ領域そのものを直接破棄する **`Intrinsic`（`name: "__builtin_free"`）ノードを挿入**する。
4. 解放ノードの挿入が完了した後、その変数の状態を `Moved`（または `Destroyed`）へと遷移させる。これにより、二重解放（Double Free）の挿入を構造的に防止する。

*注意：状態が `Moved` である変数、および型が参照型（`&T` や `&mut T`）である変数に対しては、スコープを抜ける際であっても解放命令を挿入してはならない（MUST NOT）。*

## 5. 中間表現仕様（JSON AST / IR）の拡張定義 (IR Extensions)

拡張されたシステムを表現するため、中間表現仕様（仕様書「中間表現仕様書」）のノード定義を以下のように拡張・追加する。

### 5.1 `FunctionDecl` ノードへの `isMut` フィールドの追加

関数およびクラスメソッドの可変性をバックエンド（特にC言語の restrict 最適化）へ伝えるため、`isMut` ブーリアンフィールドを必須とする（MUST）。

```json
{
    "type": "FunctionDecl",
    "name": "addAssign",
    "access": "public",
    "isMut": true,
    "typeParams": [],
    "params": [
        { "name": "other", "resolvedType": "&i32" }
    ],
    "returnType": "void",
    "body": [...]
}

```

### 5.2 `BorrowExpr` ノードの新規追加

明示的な借用演算子 `&` および `&mut` を表現する式ノードを定義する。

```json
{
    "type": "BorrowExpr",
    "isMut": true,
    "expr": {
        "type": "Identifier",
        "name": "a",
        "resolvedType": "i32"
    },
    "resolvedType": "&mut i32"
}

```

| フィールド | 型 | 説明 |
| --- | --- | --- |
| `type` | string | 固定値 `"BorrowExpr"` |
| `isMut` | boolean | `&mut` の場合は `true`、`&` の場合は `false` |
| `expr` | ASTNode | 借用対象となる式（通常は `Identifier` または `MemberAccess`） |
| `resolvedType` | string | 単一化・解決済みの完全な参照型名（`"&T"` または `"&mut T"`） |

## 6. バックエンド実装ガイドライン (Backend Code Generation)

各バックエンド（C言語変換、WASM生成、実行エンジン）の実装者は、フロントエンドが保証した安全性を前提とし、以下のマッピングルールに従って機械的にコードを生成しなければならない（MUST）。

### 6.1 C言語生成バックエンド (GCC -O2 ターゲット)

フロントエンドが明示した `resolvedType` と `isMut` を最大限に活用し、GCCの最適化能力を極大化する。

#### 6.1.1 型のマッピングルール

* 所有権型（`i32` など） $\rightarrow$ 構造体ポインタ（例：`i32*`）
* 不変参照型（`&i32`） $\rightarrow$ **`const i32*`** （読み取り専用ポインタとして lower）
* 可変参照型（`&mut i32`） $\rightarrow$ **`i32* const __restrict__`** （または `i32* restrict`）

可変参照型に対して **`restrict` 修飾子** を強制出力することで、GCCの `-O2` 最適化パスは「このポインタが指す領域は、現在のスコープ内で他の一切のポインタと重複（エイリアス）していない」と完全に確信できる。これにより、不要なメモリロード命令が完全に削除され、レジスタをフル活用したループ展開・SIMDベクトル化コードが自動生成される。

#### 6.1.2 自動挿入された命令の lower

* `__builtin_free` ノード $\rightarrow$ 標準 C ライブラリの `free(ptr)` またはバックエンド固有のアロケータ解放命令へ直変換する。
* `MethodCall { method: "drop" }` $\rightarrow$ 通常のC関数呼び出し（例：`Array_drop(ptr)`）へ lower する。

### 6.2 実行エンジン（TypeScript版インタープリタ）

仕様書「実行エンジン仕様書」に定義されたインタープリタにおける実装変更。

#### 6.2.1 オブジェクトの参照セマンティクスと BorrowExpr の評価

エンジン内部において、すべての `ObjectValue` は JavaScript のオブジェクト参照（ポインタ）として保持されている。

* `BorrowExpr` を評価する際、エンジンは新しいオブジェクトを生成せず、**ターゲットとなる `ObjectValue`（または PrimitiveValue を包むラッパーアドレス）の参照をそのまま返す**。これにより、実行時オーバーヘッドは完全にゼロ（ゼロコスト借用）となる。

#### 6.2.2 自動挿入された `__builtin_free` の処理

`evalIntrinsic` 内において、自動挿入された `__builtin_free` を受領した際、エンジンは `HeapManager.free(addr)` を実行し、JavaScript の `Map` 内部から該当アドレスのランタイム値を即座に削除（`delete`）しなければならない。
フロントエンドによって二重解放や解放後アクセス（Use After Free）は100%排除されているため、エンジン側での生存チェック（バリデーション）は省略してよい（高速化のため）。

## 7. 仕様の自己矛盾がないことの証明 (Verification & Consistency)

* **Q. 演算子 `a + &b` で `a` の所有権が消滅しないのはなぜか？**
A. §3.3 の特例ルールにより、`a` は `&a`（不変参照）としてメソッドにバインドされるため。メソッド `operator+` も引数として所有権（`i32`）ではなく不変参照（`&i32`）を要求するように定義されているため、`a` も `b` も所有権は一切消費されず、生存期間の終端まで所有権が維持される。
* **Q. バックエンドで `restrict` を付けて本当に安全なのか？ 未定義動作（UB）にならないか？**
A. フロントエンドのフェーズ3（借用チェッカー）が、同一スコープ内で `&mut T` が他の参照と被らないことを完全にチェックし、違反をコンパイルエラーとして弾いているため、バックエンドが `restrict` を付与してコンパイルしても100%安全であり、未定義動作は発生しない。
