# 📄 mozaicScript 言語仕様書 (Formal Specification)

## 1. 凡例および適合性 (Terminology & Compliance)

本仕様書における文言の解釈は、以下の定義に従う。

- **必須である（MUST / REQUIRED）：** その規定に従うことが絶対的な要件である。反する挙動はコンパイルエラーとなる。
- **禁止される（MUST NOT / PROHIBITED）：** その規定に反する挙動は絶対的な禁止事項（コンパイルエラー）である。
- **実装依存（IMPLEMENTATION-DEFINED）：** 挙動は各コンパイラバックエンドの実装に委ねられる。ただし、実装者はその挙動を文書化しなければならない。

コアライブラリの仕様については「mozaicScript コアライブラリ仕様書」を参照すること。
所有権・借用システム（メモリ安全性の自動化）については本仕様書 §4.8〜4.10（所有権型・参照型）、§5.7〜5.8（借用演算子・自動レシーバー参照バインド）、§10.4〜10.5（借用チェッカーパイプライン・バックエンドマッピング）で規定する。

## 2. ファイル種別 (File Types)

mozaicScriptは2種類のファイル拡張子を定義する。

| 拡張子 | 用途 | `_m32` 等の使用 | リテラルのコンストラクタ引数 |
|--------|------|-----------------|------------------------------|
| `.moz` | 一般ユーザーコード | 禁止 | 許可 |
| `.moc` | コアライブラリ専用 | 許可 | 許可 |

- `.moz` ファイル内で `_m8`, `_m16`, `_m32`, `_m64`, `_m128`, `_m256`, `_m512` を型として使用した場合、コンパイルエラーとする（**MUST NOT**）。
- `.moc` ファイルはコンパイラが特権モードで処理する。
- すべてのファイルは、明示的な `import` 宣言なしに他ファイルの定義を使用することはできない（**MUST NOT**）。

## 3. データ表現とメモリモデル (Data Representation & Memory Model)

### 3.1 ビット系列プリミティブ（組み込み型）

`.moc` ファイル内でのみ使用可能な、コンパイラが直接認識するデータプリミティブを以下に定義する。これらはすべて意味（解釈）を一切持たない不透明なビットの塊（Opaque Bit Pattern）である。`_mN` は2の冪乗のみ定義する。

| 型 | サイズ | 位置づけ |
|---|---|---|
| `_m8` | 8bit | 量子化・組み込み（int8量子化・MLP軽量化） |
| `_m16` | 16bit | 量子化・fp16（fp16 / int16量子化・MLP軽量化） |
| `_m32` | 32bit | 現行32bit CPU |
| `_m64` | 64bit | 現行64bit CPU |
| `_m128` | 128bit | SIMD / 将来の128bit CPU予約 |
| `_m256` | 256bit | SIMD / 将来の256bit CPU予約 |
| `_m512` | 512bit | SIMD（AVX-512）/ 将来の512bit CPU予約 |

### 3.2 メモリ空間とポインタの定義

mozaicScriptにおけるメモリ表現は、単一のフラットなアドレス空間（ヒープ領域）として抽象化される。

- **ポインタの表現：** メモリのアドレスは、ターゲットアーキテクチャの標準に応じて `_m32` または `_m64` 型の値として表現される。実際のサイズは実装依存とする。
- **アドレス単位：** バイトアドレス（1単位＝1バイト）とする。
- **ヌルポインタ：** アドレス `0` をヌルポインタとして定義する。

## 4. 型システム (Type System)

### 4.1 完全型明示（型推論の禁止）

コンパイラは、いかなる文脈においても**型推論を行ってはならない（MUST NOT）**。すべての識別子定義には、明示的な型アノテーションの付与を必須とする。

### 4.2 リテラル型の完全禁止

値そのものを型として扱う「リテラル型」は**禁止される**。型アノテーションに記述できるのは、有効な型識別子（クラス名、ジェネリクス適用型、またはビット系列プリミティブ）のみである。

### 4.3 `any` 型の禁止

`any` 型は仕様上存在しない。いかなる文脈でも使用することは**禁止される（MUST NOT）**。

### 4.4 暗黙的型変換の禁止

暗黙的型変換はいかなる場合も禁止される（**MUST NOT**）。すべての型変換は明示的なメソッド呼び出しまたはコンストラクタによって行わなければならない。

### 4.5 型エイリアス

`type` キーワードで型エイリアスを定義できる。エイリアスと元の型はコンパイラ内部で完全に同一の型として扱われる（**MUST**）。

```typescript
// 構文
type 識別子 = 既存の型;
```

- `.moz` / `.moc` 両方で使用可能。
- ジェネリクス型にも適用可能。

### 4.6 型の同一性（Type Identity）

2つの型は、**型名および型引数がすべて一致する場合に同一の型とみなす**。型エイリアスは元の型と同一とみなす。

```
i32 == i32                ✅
i32 == u32                ❌
Array<i32> == Array<i32>  ✅
Array<i32> == Array<f32>  ❌
string == Array<char>     ✅
char == u32               ✅
i32 == &i32               ❌  （所有権型と参照型は別の型）
&i32 == &mut i32          ❌  （不変参照と可変参照は別の型）
```

所有権修飾子（`&`, `&mut`）が異なる場合は完全に別の型として処理しなければならない（**MUST**）。`i32` から `&i32` への自動変換、`&mut i32` から `&i32` への自動キャストはいかなる文脈でも禁止される（**MUST NOT**、§4.4）。

### 4.7 ジェネリクス（型パラメータ）

クラスおよび関数は、任意の型パラメータを受け取る表現（例：`ClassName<T>`）をサポートする。型制約（`<T extends SomeClass>` 相当）は将来拡張予定とする。

- 呼び出し時に型パラメータを明示することを必須とする（**MUST**）。
- コンパイラは具体的な型で単一化（Monomorphization）を行い、単一化後に型エラーが発生した場合はコンパイルエラーとする。

```typescript
// ✅ 型パラメータを明示
identity<i32>(new i32(10));

// ❌ 型パラメータの省略
identity(new i32(10));
```

### 4.8 所有権型（Ownership Type）

- **表記：** 既存の型名そのもの（例：`i32`, `Array<f32>`）。
- **意味論：** その値のメモリ領域を直接管理する唯一の「所有者」であることを示す。ある時点で値の所有者は必ず世界に1つだけでなければならない。スコープの離脱または生存期間の終端において、所有権が他へ移動していない場合、そのメモリは強制的に破棄される。

### 4.9 不変参照型（Shared Reference Type）

- **表記：** 型名の先頭に `&` を付与する（例：`&i32`, `&Array<f32>`）。
- **意味論：** 値の所有権を持たず、対象を「読み取り専用」として一時的に借用する。同一の値に対する不変参照は、同一の生存期間内に同時に無限個存在することを許可する（**MAY**）。ただし可変参照（§4.10）とは絶対に共存できない（**MUST NOT**）。不変参照型を経由したフィールドへの代入や可変メソッドの呼び出しは、コンパイルエラーとしなければならない（**MUST NOT**）。

### 4.10 可変参照型（Exclusive Reference Type）

- **表記：** 型名の先頭に `&mut ` を付与する（例：`&mut i32`, `&mut Array<f32>`）。
- **意味論：** 値の所有権を持たず、対象を「読み書き可能」として一時的に借用する。可変参照はその生存期間内において世界にただ1つしか存在してはならない（排他性、**MUST**）。他の不変参照・可変参照と同一の値に対して同時に共存することは一切禁止される（**MUST NOT**）。可変参照型を経由したフィールドへの代入と可変メソッドの呼び出しが許可される。

## 5. 構文規則 (Syntax Rules)

### 5.1 リテラルの許可範囲

リテラル（数値・真偽値・文字リテラル）は型を持たない純粋な構文要素であり、型システムの管轄外とする。

- 数値・真偽値・文字リテラルを記述できるのは **クラスのコンストラクタ引数位置のみ** とする（`.moz` / `.moc` 両方）。コンストラクタはリテラルを対応するビット系列プリミティブへ内部変換する（§6.4）。
- 文字列リテラル（`"..."`）は `.moz` / `.moc` 両方で使用可能。コンパイラは文字列リテラルを `Array<u32>` のインスタンス化へ自動展開する。展開の詳細はコアライブラリ仕様書を参照すること。
- それ以外の文脈でのリテラル記述はコンパイルエラー。

```typescript
// ❌ 禁止される記述（コンパイルエラー）
let a: i32 = 10;

// ✅ 正しい記述
let a: i32 = new i32(10);

// ✅ 文字列リテラルは .moz でも使用可能（自動展開される）
const s: string = "hello";
```

### 5.2 変数および定数の宣言（完全インスタンス化義務）

すべての変数は例外なくクラスのインスタンスでなければならない。初期値には、必ず `new` キーワードによるインスタンス化、またはインスタンスを返す式・関数を記述しなければならない。すべての宣言文は末尾にセミコロン（`;`）を必須とする。

- **可変変数（`let`）：** `let 識別子: 型 = 初期値式;` （宣言後の再代入を許可）
- **不変定数（`const`）：** `const 識別子: 型 = 初期値式;` （宣言後の再代入を禁止）

`const` への再代入はフロントエンドがコンパイルエラーとして検出しなければならない（**MUST**）。バックエンド・実行エンジンは `const` の制約を意識しなくてよい。

### 5.3 関数宣言

すべての関数は `function` キーワードによって定義され、引数および戻り値の型アノテーションを省略してはならない（**MUST NOT**）。関数は値として扱うことができない（将来追加予定）。

- 戻り値の型が `void` 以外の関数において、すべてのコードパスに `return` 文が存在しなければならない（**MUST**）。
- `void` 関数における `return` 文は省略可能。

**`mut` 修飾子（クラスメソッド）：** クラスメソッドが `this` の内部状態（フィールド）を書き換える、または他の `mut` メソッドを呼び出す場合、`function` キーワードの前に `mut` を付与しなければならない（**MUST**）。`mut` を持たないメソッドの `this` は不変参照型（`&クラス名`）として扱われ、`mut` を持つメソッドの `this` は可変参照型（`&mut クラス名`）として扱われる（§6.6、§4.9/4.10）。

構文（`gpu` 修飾子と組み合わせる場合を含む）:

```
アクセス修飾子 [mut] [gpu] function 識別子<T>(引数名: T): 戻り値型 { ... }
```

```typescript
public function 識別子<T>(引数名: T): T {
    return 引数名;
}
```

### 5.4 制御構文

`if`, `for`, `while` 文の構文はTypeScriptと同一である。ループ内で宣言される一時変数であっても、5.2項に基づき `new` によるインスタンス化および型アノテーションを省略することはできない。

```typescript
for (let i: i32 = new i32(0); i < limit; i = i + new i32(1)) { ... }
```

**コンパイラの脱糖ルール：**

| ユーザーコード | 脱糖後 |
|----------------|--------|
| `if (expr)` | `__builtin_if(expr)` |
| `while (expr)` | `__builtin_while(expr)` |
| `a <= b` | `a < b \|\| a == b` |
| `a >= b` | `a > b \|\| a == b` |

### 5.5 `break` 文

- `break` 文は `while` / `for` ループ内でのみ使用可能。
- `break` は直近のループのみを即時終了する。
- ループ外での `break` 使用はコンパイルエラー。
- `continue` は仕様に含めない。

### 5.6 スコープ規則

- ブロックスコープ（`{}` 単位）を採用する。
- 内側のブロックから外側の変数へのアクセスは可能。
- 外側のブロックから内側の変数へのアクセスはコンパイルエラー。
- 同名変数のシャドーイングはコンパイルエラー（**MUST NOT**）。
- 関数のスコープは独立しており、クロージャはサポートしない（将来追加予定）。

### 5.7 借用演算子 `&` / `&mut`

値から参照を生成する際は、式中で借用演算子を明示しなければならない（**MUST**）。

```typescript
let a: i32 = new i32(10);
let b: &i32 = &a;         // ✅ 不変参照を明示
let c: &mut i32 = &mut a; // ✅ 可変参照を明示
let d: &i32 = a;          // ❌ 暗黙変換は禁止（コンパイルエラー）
```

### 5.8 自動レシーバー参照バインド（Auto-receiver-bind）

§4.4（暗黙変換の禁止）の例外として、メソッド呼び出しのドット演算子および二項演算子の**左辺のみ**、コンパイラが以下の脱糖をフロントエンドとして適用する。

変数 `x`（型 `T`）に対して `x.method(args)` または演算子 `x OP args` が呼ばれたとき：

1. メソッドが `mut` 修飾子を持つ場合（`this` の要求型が `&mut T`）：フロントエンドは `(&mut x).method(args)` として処理する。
2. メソッドが `mut` 修飾子を持たない場合（`this` の要求型が `&T`）：フロントエンドは `(&x).method(args)` として処理する。

この挙動は「型変換」ではなく「メソッド呼び出し構文のレシーバーバインド」として位置づけられる。**引数（`args` 位置）に対する暗黙変換は依然として禁止**（**MUST NOT**）されており、引数位置には `&` / `&mut` を明示しなければならない。

```typescript
let a: i32 = new i32(10);
let b: i32 = new i32(20);

let c: i32 = a + &b;  // 脱糖後: (&a).operator+(&b)
a.addAssign(&b);      // 脱糖後: (&mut a).addAssign(&b)
```

## 6. クラスと演算子オーバーロード (Classes & Operator Overloading)

### 6.1 アクセス修飾子

クラス・メソッド・フィールドすべてにアクセス修飾子を明示することを必須とする（**MUST**）。省略はコンパイルエラー。

| 修飾子 | アクセス可能な範囲 | ステータス |
|--------|------------------|------------|
| `public` | どこからでも | ✅ 実装済み |
| `private` | クラス内部のみ | ✅ 実装済み |
| `mocp public` | `.moc` ファイル内のみ（`.moz` からアクセス不可） | ✅ 実装済み |
| `protected` | クラス内部と継承先 | 🔒 予約語（将来追加予定） |

- `mocp` は単独のアクセス修飾子ではなく、**ファイルスコープ制限修飾子**である。必ず `public` と組み合わせて `mocp public` の形で記述する（**MUST**）。`mocp` 単独での使用はコンパイルエラー。
- `mocp public` メンバーは `.moc` ファイル内でのみアクセス可能であり、`.moz` ファイルからのアクセスはコンパイルエラーとする（**MUST NOT**）。
- `protected` はキーワードとして予約されるが、現バージョンでは使用した場合コンパイルエラーとする。
- コンストラクタのアクセス修飾子は `public` のみ許可する。
- クラスに定義できるコンストラクタは **1つのみ** とする（**MUST**）。

### 6.2 純粋オブジェクト指向

コンパイラは `i32`, `u32`, `f32`, `boolean` などの基本型をコンパイラ組み込みの型として**直接提供してはならない（MUST NOT）**。これらはすべて `.moc` ファイル内で通常のクラスとして実装されなければならない。

### 6.3 エクスポートルール

- `public` なクラス・メンバーは自動的にエクスポートされ、ファイル外からインポート可能となる。
- `mocp public` メンバーはエクスポートされない（`.moc` ファイル内限定）。
- `export` キーワードは不要（`public` が兼ねる）。

### 6.4 基本クラスのリテラル・コンストラクタ規則

標準ライブラリの基本型クラスのコンストラクタは、**`.moz` / `.moc` 両方で生のリテラル値を直接受け取ることができる**。コンパイラは、コンストラクタ引数にリテラル値が渡された場合、自動的にそれを対応するビット系列プリミティブへと内部変換して処理しなければならない（**MUST**）。なお `.moz` ファイルでは `_m32` 等のビット系列プリミティブを型として記述することは依然として禁止であり（§2）、リテラルはコンストラクタ引数位置でのみ許可される。

### 6.5 演算子オーバーロードの仕様

クラスの内部において、特定の特殊メソッド名を定義することで、演算子の挙動を拡張（オーバーロード）できる。

| 演算子表現 | 内部メソッド名 |
|------------|--------------|
| `a + b` | `operator+(other: T): R` |
| `a - b` | `operator-(other: T): R` |
| `a * b` | `operator*(other: T): R` |
| `a / b` | `operator/(other: T): R` |
| `a % b` | `operator%(other: T): R` |
| `a == b` | `operator==(other: T): boolean` |
| `a < b` | `operator<(other: T): boolean` |
| `a > b` | `operator>(other: T): boolean` |
| `a \|\| b` | `operator\|\|(other: T): boolean` |
| `a && b` | `operator&&(other: T): boolean` |
| `!a` | `operatorNot(): boolean` |
| `-a` | `negate(): R` |
| `a[i]` | `operator[](index: I): R` |
| `a[i] = v` | `operator_set[](index: I, value: V): void` |

単項マイナス `-a` は、慣習的な `operator*` 名ではなく通常メソッド `negate()` への呼び出しに脱糖される（コアライブラリ仕様の `negate()` と対応）。`negate()` を持たない型（`u32` / `u64` など符号なし整数）に対する単項マイナスはコンパイルエラーとする（**MUST NOT**）。なお `new i32(-1)` のようにコンストラクタ引数のリテラルに付く負号は、メソッド呼び出しではなくリテラル値そのものの否定として扱われる。

### 6.6 `this` の挙動

`this` はクラスのメソッド・コンストラクタ内でのみ使用可能で、そのインスタンス自身を指す。

コンパイラは `this` の型をメソッドの `mut` 修飾子の有無によって以下のとおり決定しなければならない（**MUST**）。

| メソッドの宣言 | `this` の型 |
|---|---|
| `mut` 修飾子あり | `&mut クラス名`（可変参照、フィールド書き換え・可変メソッド呼び出し可） |
| `mut` 修飾子なし | `&クラス名`（不変参照、読み取り専用） |

```typescript
// 具体例 (core.moc)
public class i32 {
    private let bits: _m32;

    // 不変メソッド: this は &i32
    public function operator+(other: &i32): i32 {
        let raw: _m32 = __builtin_i32_add(this.bits, other.bits);
        return new i32(raw);
    }

    // 可変メソッド: this は &mut i32 → bits への代入が許可される
    public mut function addAssign(other: &i32): void {
        this.bits = __builtin_i32_add(this.bits, other.bits);
    }
}
```

`this` が `&クラス名`（不変参照）であるメソッド内からのフィールド代入、または `mut` メソッドの呼び出しはコンパイルエラーとしなければならない（**MUST NOT**）。

| 用途 | 可否 |
|------|------|
| メンバへのアクセス（`this.x` / `this.f()`） | ✅ 許可 |
| 返り値にする（`return this;`） | ❌ 禁止（ダングリング参照防止のため） |
| 引数として渡す（`f(this)`） | ✅ 許可（要求型が参照型に一致する場合のみ） |
| クラス外での使用 | ❌ 禁止 |

### 6.7 再帰的な型定義

- `.moz` ファイル内でクラスが自分自身を直接メンバの型として参照することは**禁止される（MUST NOT）**。
- `.moc` ファイル内では `_m32` / `_m64` などのポインタ経由でのみ自己参照を許可する。

## 7. モジュールシステム (Module System)

### 7.1 インポート構文

```typescript
// 名前空間付きインポート
import "./math.moz" as Math;

// グローバル展開（明示的）
import "./core.moc" as *;
```

- `as 識別子` または `as *` のどちらかを必ず明示する（省略はコンパイルエラー）。
- `as *` でインポートしたファイル同士で名前衝突が発生した場合はコンパイルエラー。
- `as 識別子` 同士で識別子が衝突した場合もコンパイルエラー。
- インポートパスは相対パスで記述する。
- 拡張子（`.moz` / `.moc`）は省略禁止。
- `import` 文はファイルの先頭にのみ記述可能。
- 循環インポートはコンパイルエラーとする。
- `.moz` から `.moc` をインポートした場合、`mocp public` メンバーはアクセス不可。

## 8. 例外およびエラーハンドリング (Error Handling)

mozaicScriptは `try`, `catch`, `throw` といった例外専用の制御構造を**一切持たない（MUST NOT）**。エラーハンドリングはすべて `Result<T>` および `Option<T>` を用いた明示的なオブジェクトの伝播によって行う。

| 状況 | 使う型 |
|------|--------|
| 処理が失敗した（理由がある） | `Result<T>` |
| 単に値がなかった（エラーではない） | `Option<T>` |

**`__builtin_sizeof` のサイズ決定ルール**

バックエンド・エンジンは以下のルールに従って `targetType` のバイト数を決定しなければならない（**MUST**）。

- クラス定義の `private` フィールドに含まれるビット系列プリミティブの合計サイズをそのクラスのサイズとする
- `_m8` = 1バイト、`_m16` = 2バイト、`_m32` = 4バイト、`_m64` = 8バイト、`_m128` = 16バイト、`_m256` = 32バイト、`_m512` = 64バイト

```
// 例
i32  → private let bits: _m32 → 4バイト
i64  → private let bits: _m64 → 8バイト
```

## 10. コンパイラアーキテクチャと中間表現 (Compiler Architecture & IR)

### 10.1 フロントエンドとバックエンドの分離

コンパイラの処理系は、フロントエンド（構文解析・静的解析）とバックエンド（コード生成）を完全に分離独立させなければならない（**MUST**）。

- **フロントエンドの義務：** ソースコードを読み込み、構文解析・演算子オーバーロードの脱糖・型チェック・ジェネリクスの単一化を行った結果である**抽象構文木（AST）を、構造化された単一のJSON形式のデータとして出力しなければならない**。
- **バックエンドの義務：** JSON形式のAST（中間表現）のみをインプットとして動作し、各種ターゲットコードを生成しなければならない。

### 10.2 ターゲットアーキテクチャ（ドキュメント義務）

ターゲットアーキテクチャはすべて実装依存とする。各バックエンド実装者は以下を文書化しなければならない（**MUST**）。

| 項目 | 説明 |
|------|------|
| 対象ターゲット | x86-64、ARM64、WASM、TypeScriptなど |
| `_m32` 等のプリミティブの実際のサイズ | 32bit環境か64bit環境か |
| 文字コード | UTF-32、ASCIIなど |
| `__builtin_*` 命令の実際のマッピング | ネイティブ命令、WASMオペコードなど |
| 数値オーバーフロー時の挙動 | ラップアラウンド、パニックなど |
| 境界外アクセス時の挙動 | パニック、未定義動作など |
| 解放後アクセス・二重解放の挙動 | パニック、未定義動作など |

### 10.3 最適化パスの要件

コンパイラは以下の最適化パスを実装してもよい（**OPTIONAL**）。実装する場合、最適化前後のプログラムは意味的に等価でなければならない（**MUST**）。

#### プリミティブラッパーのスカラー化（Unboxing）

単一の `_mXX` フィールドのみを持つクラス（プリミティブラッパークラス）を検出し、ヒープ割り当てをスカラー変数として出力してもよい。コンパイラはクラスを**構造的に**プリミティブラッパーと判定しなければならず（**MUST**）、クラス名をハードコードしてはならない（**MUST NOT**）。

#### アロケーション省略（Allocation Elision）

`new` によるインスタンス化の結果がスタックフレームを超えてエスケープしないことが静的に証明できる場合、ヒープ割り当てをスタック変数として出力してもよい。エスケープ解析の方法・精度は実装依存とする（**IMPLEMENTATION-DEFINED**）。

#### デバッグ情報出力

Cコードを生成するバックエンドは、元の `.moz` / `.moc` ソースファイルの行番号情報を `#line` ディレクティブとして出力することを推奨する（**RECOMMENDED**）。これにより GDB 等のデバッガで元ソースの行番号によるステップ実行が可能になる。他のバックエンド（WASM 等）においても、ターゲットフォーマットが規定するデバッグ情報（DWARF、ソースマップ等）の出力を推奨する。

**マルチスレッドのターゲット別実装方針**

| ターゲット | スレッド実装 | スイッチ方式 | ミューテックス |
|---|---|---|---|
| C（x86） | pthread | プリエンプティブ | pthread_mutex |
| WASM-mt | WASMスレッド | プリエンプティブ | WASMアトミック |
| WASM-st | ジェネレーター | コオペラティブ | no-op |
| TypeScript | ジェネレーター | コオペラティブ | no-op |

- WASM-st / TypeScript のコオペラティブ実装では、バックエンドはループ先頭・関数呼び出し前後などに `yield` ポイントを自動挿入することでコンテキストスイッチを実現する。`yield` の挿入粒度は実装依存とする（**IMPLEMENTATION-DEFINED**）。コオペラティブ環境ではミューテックスをno-opとして実装してよい。
- WASMスレッドにはSharedArrayBufferが必要であり、ブラウザ環境ではHTTPSおよびセキュリティヘッダーの設定が必要となる場合がある。バックエンドはWASM-mt版とWASM-st版の2種類のバイナリを出力しなければならない（**MUST**）。ホスト側はSharedArrayBufferの利用可否を起動時に検出し、適切なバイナリを選択する。

### 10.4 フロントエンド処理フェーズ（借用チェッカー含む）

所有権の検証と自動解放命令挿入のため、フロントエンドの処理を以下の4フェーズに完全分離して実装しなければならない（**MUST**）。

```
[ソースコード]
      │
      ▼
【フェーズ1: パース & AST構築】───── 構文ツリー生成（BorrowExpr等の抽出）
      │
      ▼
【フェーズ2: 型解決】──────────────── ジェネリクス単一化・resolvedType の埋め込み
      │
      ▼
【フェーズ3: 借用チェック & Drop挿入】 所有権シミュレーション、ルール違反の検出、
                                         __builtin_free / drop の AST への自動挿入
      │
      ▼
【フェーズ4: JSON エクスポート】──── バックエンド向け JSON AST の出力
```

**フェーズ3の変数状態空間：**

| 状態 | 説明 |
|------|------|
| `Alive(Owner)` | 所有権を持って生存中 |
| `Moved` | 所有権が移動済み（実体が空） |
| `BorrowedImmutable(Count)` | 不変借用中（Count = 現在アクティブな参照数） |
| `BorrowedMutable` | 可変借用中 |

**フェーズ3の検証ルール（違反時はコンパイルエラー、MUST）：**

1. **Use After Move：** 状態が `Moved` の変数に対する読み取り・代入・メソッド呼び出し・借用生成は禁止。
2. **借用排他ルール（XOR原則）：**
   - `BorrowedImmutable(Count > 0)` の間、同変数への可変借用生成・所有権ムーブ・`mut` メソッド実行・直接代入は禁止。
   - `BorrowedMutable` の間、同変数への新たな借用生成・所有権ムーブ・あらゆる読み書きは禁止。
3. **ダングリング参照の禁止：** 参照（`&T` / `&mut T`）の生存期間が元の変数のスコープを超えるコードパスが存在する場合、コンパイルエラーとする。ローカル変数への参照を関数から返すことは100%コンパイルエラーとしなければならない。

**解放命令の自動挿入ルール：**

状態が `Alive(Owner)` の変数がスコープの終端（`BlockStmt` 末尾）または生存期間の終端に達したとき、フロントエンドは以下をASTに挿入しなければならない（**MUST**）：

1. クラスが `public function drop(): void` を持つ場合：対象変数をレシーバーとする `MethodCall { method: "drop" }` ノードを挿入する。
2. 上記の後（または `drop` を持たない場合）：`Intrinsic { name: "__builtin_free" }` ノードを挿入する。
3. 挿入後、その変数の状態を `Moved`（または `Destroyed`）へ遷移させる（二重解放防止）。

`Moved` 状態の変数および参照型（`&T`, `&mut T`）の変数には解放命令を挿入してはならない（**MUST NOT**）。

**フロントエンドとバックエンドの責任分離（**MUST**）：**

- **フロントエンド：** 上記フェーズ3のチェックと自動挿入をすべて行い、安全性が保証された JSON AST を出力する。
- **バックエンド：** 所有権の追跡・借用の検証を行ってはならない。フロントエンドが挿入した `drop` / `__builtin_free` を上から順に機械的に lower するのみ。

### 10.5 バックエンドにおける所有権型のマッピング

各バックエンドは以下のルールに従って所有権型・参照型をターゲット表現に lower しなければならない（**MUST**）。

#### C言語バックエンド

| mozaicScript 型 | C 表現 |
|---|---|
| 所有権型 `T` | `T*`（構造体ポインタ） |
| 不変参照型 `&T` | `const T*` |
| 可変参照型 `&mut T` | `T* restrict`（GCC の `-O2` 最適化が `restrict` を活用してエイリアスなしと確信できるため） |

可変参照型に `restrict` を付与することで、GCC は「現在のスコープ内でこのポインタが指す領域は他のポインタと重複しない」と確信し、不要なメモリロードの削除・レジスタ活用・SIMD化が可能になる。フロントエンドが借用排他ルールを保証するため、これは未定義動作を起こさない。

#### 実行エンジン（TypeScript インタープリタ）

- すべての `ObjectValue` は JavaScript のオブジェクト参照として保持されるため、`BorrowExpr` の評価はターゲットの `ObjectValue` 参照をそのまま返す（ゼロコスト借用）。
- 自動挿入された `__builtin_free` 受領時、`HeapManager.free(addr)` を実行する。フロントエンドが二重解放・UAF を排除済みであるため、エンジン側の生存チェックは省略してよい（高速化のため）。

## 14. GPU カーネル仕様 (GPU Kernels)

本章は GPU 上で実行されるコードの記述規則を定義する。GPU 関連クラスおよびホスト側ディスパッチ API はコアライブラリ仕様書 §8 を参照すること。GPU バックエンドの中間表現は IR 仕様書 Part 2（GPU IR）[`mozaicScript-ir-spec.md`](mozaicScript-ir-spec.md) §G1〜G9 で規定する。

### 14.1 適合性 (OPTIONAL)

本章の機能はすべて **OPTIONAL** である。提供しないバックエンドが存在してよい。ただし提供する場合、本仕様書および GPU IR 仕様書の規定に従わなければならない（**MUST**）。

### 14.2 `gpu` 修飾子

関数宣言の先頭に `gpu` 修飾子を付与することで、その関数を **GPU カーネル**として宣言できる。

```typescript
gpu function vecAdd(
    out: Ptr<f32>,
    a: Ptr<f32>,
    b: Ptr<f32>,
    n: u32,
): void {
    let i: u32 = gpuGlobalId();
    if (i < n) {
        out[i] = a[i] + b[i];
    }
}
```

#### 14.2.1 ワークグループサイズ属性

`gpu` 修飾子は属性リストを伴うことができる。属性は丸括弧で囲み、`属性名=値` の形式で記述する。

```typescript
gpu(workgroupSize=64) function vecAdd(...) { ... }
gpu(workgroupSize=[16, 16, 1]) function matMul(...) { ... }
```

| 属性 | 型 | デフォルト | 説明 |
|------|-----|-----------|------|
| `workgroupSize` | `u32` または `[u32; 1..3]` | `64` | 1 ワークグループあたりのスレッド数。スカラー値は X 次元、配列は順に X/Y/Z 次元に対応 |

属性値はコンパイル時定数でなければならない（**MUST**）。実行時に計算される値は使用できない（**MUST NOT**）。

#### 14.2.2 アクセス修飾子との組み合わせ

`gpu` 修飾子は `public` / `private` と組み合わせて記述できる。順序は `(public|private) gpu function`。`.moc` のみで使える `mocp public` との組み合わせは禁止する（**MUST NOT**）。

```typescript
public gpu function vecAdd(...) { ... }   // ✅
private gpu function helper(...) { ... }  // ✅
mocp public gpu function ... { ... }      // ❌ エラー
```

クラスメソッドへの `gpu` 修飾は本バージョンでは禁止する（**MUST NOT**）。GPU 関数はすべてトップレベルでなければならない。

### 14.3 GPU 関数内の制約

`gpu` 関数の本体には以下の制約が適用される（**MUST NOT** を伴うものは違反時にコンパイルエラー）。

#### 14.3.1 使用可能な型

`gpu` 関数の引数・ローカル変数・戻り値で使用可能な型は次に限られる。

| 種別 | 許可される型 |
|------|------------|
| 数値 | `i32`, `u32`, `f32`, `i64`, `u64`, `f64`, `boolean` |
| ポインタ | `Ptr<T>`（`T` は上記数値型または plain class） |
| 配列 | `Array<T>` のうち、CPU 側で確保され GPU 側で参照のみされるもの。要素アクセスは `arr[i]` 構文で行う |
| ユーザ定義クラス | フィールドが上記の型のみで構成され、メソッド呼び出しを行わない **plain class**（コンストラクタも禁止） |

`string`, `Result<T>`, `GpuBuffer` などの非自明型は使用禁止である（**MUST NOT**）。

#### 14.3.2 禁止される構文・操作

| 項目 | 規定 |
|------|------|
| 再帰呼び出し（直接・間接） | 禁止（**MUST NOT**） |
| 動的メモリ確保（`new`） | 禁止（**MUST NOT**）。例外: `Ptr<T>` への要素アクセスは `Ptr<T>` 自体の確保ではないので許可 |
| `__builtin_malloc` / `__builtin_free` 等のヒープ操作 | 禁止（**MUST NOT**） |
| I/O 関連（`Stdout`, `Stderr`, `Stdin`, `panic`） | 禁止（**MUST NOT**） |
| スレッド・ミューテックス・条件変数 API | 禁止（**MUST NOT**）。GPU 内同期は §14.4 のバリア命令を使用する |
| CPU 側アトミック API（`atomicLoad32` 等） | 禁止（**MUST NOT**）。GPU 内アトミックは §14.4 を使用する |
| `gpu` 関数から非 `gpu` 関数の呼び出し | 禁止（**MUST NOT**）。`gpu` 関数は他の `gpu` 関数または §14.4 の組み込みのみ呼び出せる |
| 非 `gpu` 関数から `gpu` 関数の直接呼び出し | 禁止（**MUST NOT**）。必ずホスト API（コアライブラリ §8.3 の `gpuDispatch`）経由でディスパッチする |
| 例外・パニック | 禁止（**MUST NOT**） |

### 14.4 GPU 関数内で利用可能な組み込み関数

以下の組み込み関数は `gpu` 関数内でのみ呼び出せる（**MUST NOT** 外部から呼ぶ）。実装は対応する GPU IR 命令（[IR 仕様書 Part 2 §G7](mozaicScript-ir-spec.md)）に直接 lower される。

#### 14.4.1 スレッド ID / インデックス取得

| 関数 | 説明 |
|------|------|
| `gpuGlobalId(): u32` | グローバルスレッド ID（X 次元のみ）。WGSL の `@builtin(global_invocation_id).x` に相当 |
| `gpuGlobalIdX(): u32` / `gpuGlobalIdY(): u32` / `gpuGlobalIdZ(): u32` | グローバルスレッド ID の各次元 |
| `gpuLocalId(): u32` | ワークグループ内ローカル ID（X 次元）。WGSL の `@builtin(local_invocation_id).x` に相当 |
| `gpuLocalIdX(): u32` / `gpuLocalIdY(): u32` / `gpuLocalIdZ(): u32` | ローカル ID の各次元 |
| `gpuWorkgroupId(): u32` | ワークグループ ID（X 次元） |
| `gpuWorkgroupIdX(): u32` / `gpuWorkgroupIdY(): u32` / `gpuWorkgroupIdZ(): u32` | ワークグループ ID の各次元 |
| `gpuWorkgroupSize(): u32` | カーネルに宣言された `workgroupSize` の X 次元値（コンパイル時定数） |

#### 14.4.2 同期バリア

| 関数 | 説明 |
|------|------|
| `gpuBarrier(): void` | ワークグループ内の全スレッドが本関数到達まで待機。WGSL の `workgroupBarrier()` に相当 |
| `gpuStorageBarrier(): void` | グローバルメモリ（`Ptr<T>` 経由のアクセス）の可視性同期 |

#### 14.4.3 GPU アトミック操作

GPU 内で `Ptr<u32>` / `Ptr<i32>` に対するアトミック操作を行う。CPU 側のアトミック API（コアライブラリ §6.6）とは別 API である。

| 関数 | 説明 |
|------|------|
| `gpuAtomicAdd(ptr: Ptr<u32>, val: u32): u32` | アトミック加算（加算前の値を返す） |
| `gpuAtomicSub(ptr: Ptr<u32>, val: u32): u32` | アトミック減算 |
| `gpuAtomicMin(ptr: Ptr<u32>, val: u32): u32` | アトミック最小値書き込み |
| `gpuAtomicMax(ptr: Ptr<u32>, val: u32): u32` | アトミック最大値書き込み |
| `gpuCompareExchange(ptr: Ptr<u32>, expected: u32, desired: u32): GpuCasResult` | Compare-And-Swap。戻り値は `{ oldValue: u32, exchanged: boolean }` の plain class。CPU 側 `atomicCas32`（成功/失敗 boolean）とは命名で意図的に差別化（**MUST**） |
| `gpuAtomicLoad(ptr: Ptr<u32>): u32` | アトミックロード |
| `gpuAtomicStore(ptr: Ptr<u32>, val: u32): void` | アトミックストア |

i32 版は名前末尾に `I32` を付加する（`gpuAtomicAddI32` 等。`gpuCompareExchange` の i32 版は `gpuCompareExchangeI32`、戻り型は `GpuCasResultI32`）。メモリ順序は実装が WGSL の `SeqCst` 相当を採用する（**IMPLEMENTATION-DEFINED**）。

`GpuCasResult` / `GpuCasResultI32` は plain class（フィールド `oldValue: u32 / i32`、`exchanged: boolean`）として `gpu` 関数本体内でのみ利用可能。コアライブラリで以下に定義する：

```typescript
public class GpuCasResult {
    public let oldValue: u32;
    public let exchanged: boolean;
}
public class GpuCasResultI32 {
    public let oldValue: i32;
    public let exchanged: boolean;
}
```

#### 14.4.4 ベクトル・行列ユーティリティ

`gpu` 関数内では、`Ptr<T>` を介した配列アクセス以外にベクトル演算組み込みを提供する。これらは GPU IR の SIMD ベクトル型に直接マップされる。

| 関数 | 説明 |
|------|------|
| `gpuDotF32x4(a: Ptr<f32>, b: Ptr<f32>): f32` | 4 要素 f32 内積 |
| `gpuFma(a: f32, b: f32, c: f32): f32` | `a * b + c`（融合積和） |

本セクションのベクトル組み込みは最小セットであり、将来拡張される。

### 14.5 コンパイル時検証

コンパイラは `gpu` 関数本体に対して次の検証を行わなければならない（**MUST**）。

1. §14.3.1 の型制約
2. §14.3.2 の構文・操作制約
3. §14.4 以外の組み込み（`__builtin_*` のうち §14.4 にリストされていないもの）の呼び出し禁止
4. 引数が `Ptr<T>` または上記許可済みスカラー型であること
5. 戻り値型が `void` であること（**MUST**）。GPU カーネルは値を返さず、結果は `Ptr<T>` 経由で書き戻す

違反はすべてコンパイルエラー（**MUST**）。
